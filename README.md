# Warehouse RMS2

1. **Должно быть установлено заранее:** Ubuntu 24.04, Python 3.12, `apt` и `sudo`. Источники пакетов ROS 2 Jazzy уже подключены.

2. **Установить через APT:** пакеты из [requirements-system.txt](requirements-system.txt). ROS-библиотеки, сообщения, TF, CMake и pytest устанавливаются как зависимости указанных пакетов. Выполните из корня проекта:

   ```bash
   xargs -r -a requirements-system.txt sudo apt install -y
   ```

## Сборка проекта

```bash
cd ros_ws && colcon build --symlink-install
```

## Запуск FastAPI

Один раз установите Python-зависимости из корня проекта:

```zsh
python3 -m venv --system-site-packages .venv
.venv/bin/python -m pip install -r requirements-web.txt
```

После сборки ROS-пакетов запустите сервер:

```zsh
./scripts/run-fastapi.sh
```

Веб интерфейс доступен по адресу http://localhost:8000/


Во всех трёх скриптах первый аргумент — `normal` или `stress`; по умолчанию `normal`:

```zsh
./scripts/run-simulation.sh stress
./scripts/run-fastapi.sh stress
./scripts/run-all.sh stress
```

Первые две команды запускают компоненты отдельно, третья — оба вместе с одной картой.

## Очереди VDA5050 / Mosquitto

Диспетчер поддерживает несколько роботов. Пользовательские задания `MOVE` / `PARK`
принимаются FIFO (до 16 на робота, 512 на парк). `/api/orders` возвращает `202` при
постановке в очередь; `route` может быть пустым до активации задания. Повтор одного
`order_id` с теми же параметрами не добавляет задание повторно.

```text
Web → FleetCore → VDA Master → Mosquitto → Robot Adapter → ROS Agent
```

`run-simulation.sh` запускает локальный Mosquitto, если порт `127.0.0.1:1883` свободен.
Если брокер уже работает, используется он. Для каждого добавленного робота автоматически
запускаются Agent и Robot Adapter. Скрипты используют Python из `.venv`; зависимости
MQTT (`paho-mqtt` 2.x) и JSON Schema устанавливаются из `requirements-web.txt`.
После обновления выполните установку зависимостей и сборку ROS-пакетов, затем:

```zsh
./scripts/run-all.sh normal
# Или карта с узкими проходами:
./scripts/run-all.sh stress
```

Конфигурация: `ros_ws/src/vda_bridge/config/vda5050.yaml`. Для внешнего или
аутентифицированного брокера создайте собственный YAML и задайте
`WAREHOUSE_VDA_CONFIG=/absolute/path/vda5050.yaml`. Параметры `mqtt.username_env`,
`mqtt.password_env` задают имена переменных окружения с учетными данными;
`mqtt.tls_ca` — путь к CA. Локальная конфигурация разрешает anonymous только на loopback.
Одна конфигурация используется диспетчером и всеми адаптерами. Идентификатор MQTT
по умолчанию соответствует `robot_id`; переопределения задаются в списке `robots`.

### Алгоритм планировщика пути

Построение маршрута реализовано в
[`PathPlanner`](ros_ws/src/fleet_dispatcher/fleet_dispatcher/planner.py),
а выдача разрешений на движение и разрешение блокировок — в
[`FleetCore`](ros_ws/src/fleet_dispatcher/fleet_dispatcher/core.py).

#### 1. Подготовка графа карты

При создании планировщика карта преобразуется в направленный граф `networkx.DiGraph`:

- Каждый узел карты становится вершиной графа с координатами `(x, y)`.
- Для каждого ребра добавляется переход `source → target`. Обратный переход
  добавляется только при `bidirectional = true`.
- Вес ребра `length` равен евклидову расстоянию между его концами:
  `sqrt((x₂ − x₁)² + (y₂ − y₁)²)`.

После построения структура графа фиксируется через `nx.freeze`.

#### 2. Поиск основного маршрута методом A*

Метод `find_path(start, target, blocked_nodes=())` получает идентификаторы начального
и целевого узлов, а также временно недоступные узлы:

1. Проверяет наличие обоих узлов в графе. Если узел неизвестен, возвращает ошибку
   `Неизвестный узел карты`.
2. Запускает `nx.astar_path` с весом ребра `length`. При выборе следующей вершины
   используется оценка `f(n) = g(n) + h(n)`, где `g(n)` — длина найденного пути
   от старта до вершины, а `h(n)` — расстояние по прямой от нее до цели.
3. Поиск рассматривает разрешенные направления ребер и улучшает стоимость пути
   к вершине, если найден более короткий вариант. Эвристика не превышает длину
   оставшегося пути, поэтому результат минимален по сумме длин ребер.
4. Возвращает список узлов `[start, ..., target]`, включая оба конца маршрута.
   При `start == target` результат — `[start]`. Если цель недостижима,
   возвращает ошибку `Маршрут до целевого узла не найден`.

При приеме задания диспетчер предварительно проверяет достижимость цели от цели
последнего задания в очереди либо от текущего узла робота, если очередь пуста.
При этой проверке узлы роботов без связи исключаются: если обхода нет, новый
приказ отклоняется с HTTP `409` и ошибкой «Маршрут до целевого узла не найден».
Если начальный узел еще неизвестен, проверка откладывается. При активации задания
маршрут строится заново от фактического текущего узла остановившегося робота.

Узлы роботов без связи или без синхронизированного состояния исключаются из A*.
Среди доступных путей стоимость учитывает только длину: скорость, повороты,
время ожидания, габариты и положение остальных роботов в A* не входят.
Доступность переходов проверяется на этапе исполнения; занятое ребро само по себе
не вызывает поиск альтернативного основного маршрута.

#### 3. Проверка и разрешение очередного перехода

На каждом такте диспетчер обрабатывает готовых роботов по номеру первого задания
в их очереди: более раннее задание имеет больший приоритет, при равенстве
используется `robot_id`. Участники активной цепочки освобождения наследуют
приоритет исходного задания. Перед выдачей перехода диспетчер:

1. Проверяет синхронизацию, телеметрию, подтверждение текущей версии заказа
   и остановку робота в узле. Пока предыдущий переход не завершен,
   следующий не разрешается.
2. Берет очередную пару узлов `(a, b)` и проверяет весь отрезок движения на
   конфликты с положениями и зарезервированными переходами других роботов.
   Конфликт возникает при расстоянии между отрезками не больше
   `radius₁ + radius₂ + 2 × tolerance`; радиус робота равен половине диагонали
   его корпуса. Это учитывает встречные и пересекающиеся переходы.
3. Проверяет допустимость движения по карте через `CollisionChecker`
   с радиусом `radius + tolerance`. При конфликте или недостаточном просвете
   робот остается в `WAITING` с указанием причины.
4. Если переход доступен, резервирует `(a, b)`, увеличивает версию заказа
   и разрешает ровно один переход через VDA5050 Base.
5. Снимает резервацию после подтверждения прибытия в нужный узел и остановки
   по свежей одометрии. После последнего узла завершает задание и затем
   переходит к следующему заданию очереди.

Выдаются все совместимые переходы за такт. Ожидание отмены или служебный отъезд
одного робота не останавливают независимое движение остальных. Дальний
невыданный участок обычного маршрута не резервирует коридор целиком.
Отдельная проверка не дает подходящему роботу перекрыть единственный выезд
из занятого тупика. Статический просвет кэшируется для текущей карты и габаритов;
положения и резервации проверяются при каждой выдаче.

#### 4. Освобождение пути и взаимные блокировки

Диспетчер заранее проверяет оставшийся маршрут. Приоритет имеет самое раннее
задание: его маршрут сохраняется, а мешающие роботы с более поздними заданиями
или без заданий уступают. Если мешающий робот уже может отъехать своим маршрутом,
он продолжает текущее исполнение. Иначе исполнение отменяется с подтверждением
для служебного отъезда. Пользовательские задания и порядок FIFO сохраняются.

Уступки планируются рекурсивно в `YieldPlanner`. Алгоритм Дейкстры на направленном
графе перебирает точки отъезда по длине пути, при равенстве — по ID узла.
Если путь или точку занимает другой робот, для него ищется следующий отъезд.
Конечная точка каждого отъезда должна освобождать маршрут приоритетного робота
и пути отступления предыдущих роботов с учетом габаритов. Если нижняя ветка
невыполнима, поиск возвращается к предыдущему роботу и пробует другую точку;
неудачные ветки не отправляют команд. Циклические зависимости исключаются.

Сначала проверяется рекурсивная ветка для конкретного препятствия на виртуальных
положениях, затем выполняется отъезд последнего робота. Пути предков сохраняются
как временные защиты, чтобы подходящий робот не перекрыл их выезд. После отъезда
поиск повторяется по свежей телеметрии. Независимые цепочки могут выполняться
параллельно; свободные начальные переходы пользовательских маршрутов продолжаются.

Путь уступки не может пересекать узел приоритетного робота, зафиксированный
при назначении уступки; его актуальное положение также проверяется перед
каждым переходом. В рекурсивной цепочке также запрещено пересекать узлы
предыдущих участников. После отъезда основное задание перестраивается от новой
ноды к сохраненной цели. Робот продолжает очередь по доступным переходам;
ждать завершения всего приоритетного задания не требуется. Если следующий
переход возвращает его на еще защищаемый участок, он ждет именно перед ним.
Свободный робот без заданий остается в точке отъезда.
Если подходящего отъезда нет, роботы продолжают ожидать с указанием причины.
Поиск ограничен 2000 шагами на попытку, чтобы сложная конфигурация не блокировала
обработку телеметрии; достижение лимита отображается отдельно от отсутствия пути.

Подробное описание очередей, локальных ограничений и блок-схемы:
[DISPATCHER.md](DISPATCHER.md).

### Выполнение маршрутов

Используется ограниченный профиль **VDA5050 2.1.0**. Официальные схемы и их происхождение
сохранены в `ros_ws/src/vda_bridge/protocols/vda5050/schemas/`. Поддерживаются
`order`, Base/Horizon, обновления заказа, `state`, `connection`/LWT, `factsheet`,
`cancelOrder` и `factsheetRequest`. Действия на узлах/ребрах, загрузка, зарядка,
траектории и другие instant actions не реализованы. `startPause`/`stopPause` не
объявляются в factsheet; ожидание трафика управляется границей Base.

Сначала строится полный кратчайший направленный путь. Стартовый узел передается
в Base, остальные этапы — в Horizon. Перед каждым переходом диспетчер атомарно
резервирует узлы и ребро, затем увеличивает `orderUpdateId` и разрешает один
переход. Адаптер выполняет только разрешенный переход через локальный `FollowRoute`.
Следующее разрешение выдается после остановки и подтверждения положения в узле.
Ожидание нового Base отображается как `WAITING` и не вызывает `STUCK`.

Занятые, въезжающие и уезжающие роботы блокируют конфликтующие переходы. Учитываются
также пересекающиеся ребра и габариты. Мешающие роботы рекурсивно освобождают
оставшийся маршрут самого раннего задания, пока подъезжающий робот не перекрыл
их выезд. Цепочка строится с перебором ближайших точек отъезда; путь отъезда не
пересекает узел, на котором находился ожидающий робот при назначении уступки,
даже если тот уже выехал. Актуальное положение также проверяется перед каждым переходом. После отъезда робот
остается там. Занятой робот может временно уступить, сохраняя
свои пользовательские задания. После уступки старые этапы удаляются и маршрут
строится заново. Если подходящего отъезда нет, очередь сохраняется и отображается
причина ожидания. Если следующий участник не может отъехать, предыдущему
подбирается другая точка отступления.

Панель показывает очередь, конечную цель, оставшийся маршрут, причину ожидания,
служебное перемещение, MQTT-соединение и отправленную/подтвержденную версию заказа.
Снимок публикуется в `/fleet/state` и передается через `/ws/state` в поле `fleet`.

### Доставка и восстановление

В карточке выбранного робота доступна кнопка **«Выключить робота» / «Включить робота»**.
Она отключает и восстанавливает MQTT-адаптер, симулируя потерю связи. ROS-агент
остаётся активным: робот завершает только уже разрешённый переход и затем ждёт.
Задания и их порядок в очереди сохраняются.
Новые приказы роботу без MQTT-связи отклоняются с HTTP `409` и сообщением
«Нет связи с роботом: построение маршрута невозможно»; маршрут не строится,
задание в очередь не добавляется.

Узел робота без связи исключается из поиска маршрутов и отмечается красным кругом.
Если переход ещё не подтверждён, оба его узла и резервация сохраняют блокировку
до сверки состояния. Остальные роботы перестраивают маршруты после подтверждённой
отмены в узле; при отсутствии обхода задания ожидают восстановления связи.
Такая же блокировка применяется при устаревшей телеметрии. После включения сначала
сверяется актуальное состояние, затем снимаются блокировки и продолжается очередь.
В режиме MANUAL сначала нужно выйти из ручного управления.

HTTP: `POST /api/robots/{robot_id}/connection` с `{"enabled": false}` или
`{"enabled": true}`; ROS: `/{robot_id}/set_connection_enabled` (`std_srvs/SetBool`).

Топики: `uagv/v2/WarehouseSim/{robot_id}/{order|instantActions|state|connection|factsheet}`.
Для `connection` используется QoS 1, для остальных сообщений — QoS 0.
`connection` и `factsheet` retained; команды никогда не retained.
Прием команды подтверждается по `state`, публикация не считается подтверждением.
Повторы отправляются раз в секунду; через 5 секунд без подтверждения отображается
`UNCERTAIN`, резервации сохраняются. После переподключения сначала сверяется состояние.

При потере MQTT робот завершает не более одного уже разрешенного перехода, затем
ждет. Одометрия и защита от столкновений остаются локальными. При остановке между
узлами требуется восстановление положения; ручное управление приостанавливает
выдачу новых переходов парку. После выхода из ручного режима в узле прерванный
заказ отменяется с подтверждением и перестраивается к сохраненной цели.

Очереди заданий хранятся **только в памяти RMS**. Перезапуск Mosquitto их не удаляет.
После перезапуска диспетчера старые исполнения сверяются и отменяются, а пользователь
подает задания заново. При перезапуске адаптера сохраненные команды не исполняются
автоматически. SQLite в `state_directory` хранит квитанции приема и контрольный снимок
для защиты от повторного исполнения, а не очередь пользовательских заданий.
Журналы нельзя удалять во время работы системы.

### Проверки

```zsh
.venv/bin/python -m pip install -r requirements-test.txt
.venv/bin/python -m pytest tests -q
npm test --prefix warehouse_web/frontend
source /opt/ros/jazzy/setup.zsh
source ros_ws/install/setup.zsh
RUN_ROS_TESTS=1 .venv/bin/python -m pytest tests/test_ros_vda_integration.py -q
```

Интеграционные тесты используют отдельный порт Mosquitto, ROS domain и временные
журналы; пользовательский брокер и его данные не изменяются.
